最近 Grok Bot 在我关注的圈子里引起了不少讨论。我也体验了一个开源项目 [ds-bot](https://github.com/Fei2411/DeepSeek-Bot)，尝试把不同分工的 Bot 拉进同一个群聊。

最初吸引我的，是它可以把 Agent 组织成具有稳定身份的成员。你可以创建产品经理、工程师、设计师等不同角色，让它们围绕同一个问题展开讨论，各自探索，再把结果带回群里。

过去，我更习惯于向 Agent 提出任务，等待执行，然后检查结果。这次，我开始尝试组织一个团队：让成员分工、交接、相互质疑，再由我作出最终判断。

但群聊也很快暴露出问题。有些 Bot 不断报告抓取页面、找到路径等执行细节，有些消息则没有说清结果对其他成员意味着什么。我虽然把任务分出去了，却仍然需要从大量消息中筛选进度、判断下一步该找谁。

随后，我听了 Grok Bot 相关访谈，又阅读了官方设计文章，以及 Joye 对相关讲座的整理，开始理解这种形态背后的产品与工程取舍。

**Agent 提高了一个人的执行能力，使我们可以同时推进更多工作。但人的注意力、上下文切换和协调能力，并不会同步增长。**

当执行不再是唯一的瓶颈，问题就变成了：如何组织多个 Agent，让工作持续推进，同时不让人陷入监督和协调的负担？

本文讨论的 Bot，是一种持续协作的 Agent 产品形态。它将身份、职责、记忆、事件入口和通信机制组织起来，让用户可以围绕长期成员安排工作。Chat、Agent 与 Bot 并非互斥的技术类别，也不是所有产品必然经历的演进阶段；这里关注的是，它们如何改变用户组织工作的方式。

## 一、从任务到成员：谁来持续负责

以会话或任务为中心的 Agent 产品，通常有一条清楚的使用路径：用户提出目标，Agent 调用工具，最后交付结果。

但工作一旦跨越多个任务，用户往往还需要维持它们之间的联系：恢复背景，确认上次的判断，找到已有成果，再安排后续工作。跨会话记忆可以提供帮助，却未必同时解决职责归属和工作跟进。

Grok Bot 在[官方设计文章](https://x.ai/news/designing-grok-bot)中选择了以 Bot 为中心的组织方式。设计团队面对已经积累起来的 Session、Context Window、System Prompt、Sandbox 等概念，先问用户真正需要理解哪些，最后将主要产品概念收敛到五个：

| 概念 | 用户需要理解的作用 |
| --- | --- |
| Bot | 具有身份、记忆、运行时与工具的持久 Agent |
| Chat | 与 Bot 协作的对话入口 |
| Prompt | 指令与上下文，可一次使用、保存为 Skill，或通过 Routine 自动触发 |
| Tool | 获取信息、使用软件与执行操作的能力 |
| Artifact | 工作中产生或修改的持久成果 |

底层概念仍然存在，但用户不必先理解全部实现，才能委托工作。

更重要的变化是，职责开始附着在一个可持续寻找的成员上。一个工程 Bot 可以沿用项目中的技术背景，一个研究 Bot 可以积累资料与核查经验。下次继续工作时，用户知道该找谁，也能根据过往表现调整它。

官方设计还区分了能力与经验的归属：Tool 和 Skill 可以在账户层共享，Memory 和 Routine 则跟随具体 Bot；群聊提供项目共享上下文，同时允许各成员保留专业记忆。能力可以复用，角色需要的积累也有了归属。

据此，我更愿意将这段关系概括为：**Bot 是长期存在的协作成员，群聊承载某段工作契约，话题则是协作中正在处理的事情。**

换话题不必清空成员的所有经验，结束一次协作也不必销毁成员。不过，长期记忆仍需要筛选与更新，保存下来的历史不能自动等同于当前任务所需的上下文。

### 成员还需要可配置的能力

稳定身份只是入口。要让「工程师」「研究员」这样的分工具有实际内容，还需要安排它能获取什么信息、使用什么工具，以及由什么模型承担判断。

在这次讨论中，我最初想到的是：便宜模型让多个 Bot 更容易负担。后来补上的条件是，重要职责可以投入更强的模型，边界明确的工作可以尝试低成本模型，工具也应按任务提供。

**成员配置决定长期由谁负责、具备什么能力；请求路由决定某次工作交给什么执行资源。** 两者可以并存，但仅有路由还不足以表达长期职责。

配置也不是可靠性的保证。它的价值在于，让用户有一个可以观察和持续调整的对象，再根据实际结果决定如何投入资源。

## 二、从输出到交接：哪些信息值得进入协作

群聊里那些「拿到页面了」「找到正确路径了」的消息，让我意识到：**一个 Bot 有执行进展，不代表这段进展已经对别人有用。**

假设工程 Bot 阅读了十篇文档、分析代码，并完成几轮实验。产品 Bot 可能只需要知道方案能否实现，以及哪些约束会影响需求；设计 Bot 则需要知道哪些交互应该调整。它们并不需要同步阅读每次尝试。

因此，多 Bot 协作需要区分两种信息用途：

- **成员的工作上下文：** 独立探索、工具调用、暂未证实的假设与局部细节。
- **共同的协作上下文：** 结论、分歧、重要变化、成果位置与交接要求。

这是信息组织上的区分，不等于操作系统层面的权限隔离。共享文件也不意味着文件内容必须全部进入每个成员的模型上下文。

### 发送消息，本身应当是一次判断

我在讨论中把这类显式发送动作概括为 sendmessage：让 Bot 在工作过程中主动选择是否发言、告诉谁，以及需要提供多少信息。这里是机制分析，并非指某个已经核实的 Grok Bot 内部接口；ds-bot 文档中用于向其他 Bot 发消息的工具名是 `message_bot`。

发送之前，需要理解几个问题：

1. 接收方正在负责什么，这条信息与它有什么关系？
2. 现在是否值得打断对方，还是可以等待合并汇报？
3. 对方需要结论、依据，还是明确的行动请求？
4. 详细成果在哪里，接手后能否继续工作？

文件与消息在这里互相配合。文件保存完整材料，消息说明结果的意义，以及哪里需要接手。Grok Bot 的 [Files and results 文档](https://docs.x.ai/grok-bot/files-and-results)也建议，共享工作区可用于中间材料，而对话中应包含最终结果或指向结果的清晰链接。

**静默是一种合理选择，但静默并非唯一的降噪方式。** 阶段性汇报、合并消息、只通知相关成员，同样可以减少干扰。一句「之前的阻塞已解除，正在验证后续流程」，即使不要求用户采取行动，也能让用户有依据地继续等待。

### 能通信，还不等于会协作

消息工具提供了交接条件，正确交接仍依赖成员对职责、任务状态和接收方需求的理解。

这次讨论中，对消息价值的认识就是在来回回应中形成的：过程广播暴露了问题，我提出发送前应判断什么对别人有用，成员继续补充了文件留档、接收方差异与进度可见性。讨论改变了我们对设计问题的理解。

多个 Bot 的潜在价值，也应当落到这样的变化上。例如，工程成员提出实现约束，产品成员据此修改需求，测试成员再调整验证范围。**重要的是新增信息如何改变后续判断，而不是群里出现了多少份意见。**

一个强模型也能模拟多个角色。不同模型、不同头衔，更不自动意味着盲点不同。值得验证的是：职责、材料、经验和工具形成的有效差异，能否经过相互回应改善结果。成员之间的赞同，不能替代证据与验证。

## 三、持续协作如何运转，又如何养得起

把 Bot 当作长期成员，还意味着后续工作不应总等着用户回来发下一条消息。

约定明天检查结果，需要定时触发；外部条件变化，需要事件唤醒；另一个成员完成前置工作，需要消息交接。**持续性保存任务与约定，主动性让它们在条件满足后继续生效。**

这要求系统保留可恢复的状态，并能够再次启动执行。但它并不必然推出某一种架构。

### 持续有效的委托，按需运行的环境

据 [Joye 对 Lee Robinson 讲座的整理](https://www.joyehuang.me/blog/20261011---alwaysonagents/post)，Grok Bot 将触发入口、服务端与执行环境分开：服务端负责消息调度、Agent loop 和状态保存；云端电脑提供文件、浏览器和命令执行能力，按需启动，使用后可以快照休眠；长任务通过持久化工作流支持恢复。

这项设计的关键在于：**持续的是工作状态与委托关系，计算资源可以按需使用。**

用户关心的是离开之后任务能接续、已有成果不丢失，而不是模型始终推理、云电脑始终开机。分开维护状态与执行环境，也为环境重建、维护和故障恢复提供了空间。

这些是后来阅读材料得到的架构解释，并非我在 ds-bot 中验证过的实现。它说明了一种兼顾持续性与资源开销的做法，不能直接推广成所有 Bot 系统的唯一方案。

### 成本不只由模型单价决定

长期运行首先要养得起。多成员、多轮讨论和频繁事件触发，会让单次看似不大的开销持续累积。

可以从三个层次分析成本：

| 层次 | 需要考虑的问题 |
| --- | --- |
| 调用次数 | 是否重复唤醒、重复探索，讨论是否仍有新增信息 |
| 单次调用 | 输入长度、缓存复用、输出与推理开销、模型单价 |
| 执行环境 | 活跃时间、空闲资源、存储与恢复开销 |

长期会话可能反复使用相同的指令与历史前缀。模型服务支持提示缓存时，复用满足条件的前缀可以降低重复输入费用；上下文的排列与变化方式因此会影响成本。具体命中条件、有效期和计费仍取决于服务，缓存也不能消除新输出、工具执行和额外调用的费用。

去重与合并事件、减少重复劳动，可以降低不必要的调用；压缩无关材料、按需读取工具说明，则主要影响单次输入。**减少 token 与减少调用是不同的优化手段，不能混为一谈。**

这也补全了我对便宜模型的最初判断。低成本模型扩大了可以尝试的协作范围，但团队是否划算，还取决于任务成功率、重试、讨论轮数和核验成本。重要职责值得使用更强的模型，也应根据实际表现调整。

因此，需要经营的是一套能力与成本配置：哪些成员独立探索，哪些负责综合判断，哪些结果必须验证。自建是否更划算，也需要计算基础设施与维护开销，不能只比较 API 单价。

## 四、掌握进度与授权：人如何按需介入

我希望得到的体验是：能够知道事情推进到了哪里，却不必一直盯着执行过程。

Grok Bot 官方设计文章中的一项用户研究与此有关：用户要求查看动作细节，主要是为了确认 Bot 还在工作、方向没有偏离。这个发现不意味着所有细节都没有价值，而是提醒产品区分「确认状态」与「检查过程」两种需求。

官方的电脑访问设计提供了三个层次：

| 层次 | 作用 |
| --- | --- |
| Status | 了解 Bot 当前是否在工作 |
| Preview | 需要时查看执行现场 |
| Takeover | 必要时接管操作，再交还控制权 |

**让用户随时能够了解进展，不等于让用户持续接收全部进展。** 默认提供足以判断局面的信号，再允许逐层检查，可以减少被界面诱导去监督每一步的负担。

信息的呈现形式也服务于这个目标。官方设计中的内联卡片与 Widget，可以用来展示结构化结果和明确操作；例如邮件草稿将内容与确认入口放在一起，比长段文字更便于核对。这里值得学习的是如何降低检查与决策成本，而不是为所有回复增加组件。

### 自主执行，先要理解委托范围

我们这个群也提供了一个失败案例：我想探索想法，几个 Bot 却开始派活、写稿和核查。它们协调得很积极，但推进了我没有要求的事情。

这暴露出两个需要分别解决的问题：成员是否理解当前目标，以及系统是否守住动作的授权范围。多成员彼此确认，也可能只是在共同的错误前提下继续推进。

工作委托至少应说清目标、允许的动作与资源，以及需要再次确认的条件。遇到信息不足时请人帮忙，与请求执行某项动作的授权，也需要区分。已有授权内的工作可以继续，超出范围则应停在可检查的结果上，例如准备好邮件草稿，再请求发送确认。

### 模型判断与程序约束

据 Joye 对讲座的转述，Bot 在群聊中如何表现，相关训练数据仍然不足。这不是对所有模型能力的量化结论，但提示了沟通判断需要验证，不能因为产品支持静默就认为问题已经解决。

Joye 在自己的群聊 Bot 实践中，采用了让模型决定是否回复、由程序限制发送频率与冷却时间的做法。这里需要与前面转述的 Grok Bot 架构分开理解。

从中可以提炼出一种分工：模型处理相关性、接收方和表达方式等情境判断；程序执行权限、预算与频率等明确约束。重要动作是否需要确认，应依据用户授权，而不是只听模型对风险的自我评价。

**为了补偿当前能力而添加的流程，可以在评测证明有效后调整；用户设定的边界，则需要持续执行。** 模型更强，不等于系统可以自行放宽授权。

## 五、从使用 Agent，到组织 AI 团队

回看这些设计，产品做的减法有了更具体的含义：减少用户反复介绍背景、搬运结论、催进度和阅读执行细节的劳动。

与此同时，系统需要承担更多工作：维护状态、调度事件、筛选上下文、支持交接、控制成本，并执行授权边界。模型能力提高后，某些补偿流程或许可以简化，但持续协作所需的基础能力仍然需要维护。

我对 Bot 的兴趣，也逐渐从「多个模型一起回答」，转向了如何组织一段可持续、可配置的协作关系。

主理人确定方向，为成员安排职责、模型与工具，根据表现调整团队；成员独立探索，通过消息和成果交接，暴露分歧并修正判断；重要决策仍需要有人评价与拍板。

未来的 Agent 间协作值得期待，但能够互发消息只是起点。这里讨论的是协作形态，不等同于具体的 A2A 通信协议；协议如何连接不同系统，是另一个层次的问题。

多 Bot 是否优于单个强 Agent，仍需要在具体任务上比较。对我而言，更值得继续实践的判断是：**当执行能力不断提高，好的组织与交互方式，能够让人以更少的协调劳动掌握工作，并把注意力留给判断。**

把 Agent 当作同事，最终需要落实为持续负责、有效交接和有边界的自主性。名字与角色让这种关系容易理解，系统能否兑现这些能力，才决定它是否真正有用。
