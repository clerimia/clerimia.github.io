**技术架构是对工作负载和约束条件的回应。判断一个系统是否需要重新设计，不应只问它能否继续优化，还要问它当初试图满足的约束是否依然成立。**

## 一、AI 让版本控制承受新的工作负载

在 Anthropic，AI 让编码不再是软件开发的主要瓶颈。Agent 能够大规模并行地编写、测试和修改代码，软件生产的吞吐量不再直接受限于人类逐行编码的速度。

这种变化将压力逐渐传导到了版本控制等开发基础设施。

2026 年 5 月，Anthropic 每天平均合并约 2,500 次代码变更；到了 9 月，这个数字已经超过 30,000 次，增长超过 12 倍。与此同时，其 Monorepo 主分支历史接近 100 GB，CI 系统每天需要执行约 2,500 万次代码 Checkout。

**问题不只是代码越来越多，而是仓库规模与操作频率同时增长，使得原有架构的成本被不断放大。**

## 二、Git 的离线自主性，为何变得昂贵？

Git 是一个分布式版本控制系统。它的一项核心设计目标是支持开发者离线工作，因此赋予客户端很强的自主性：开发者可以在本地查看历史、计算 Diff、创建 Commit，而不必每次都访问服务器。

但这种自主性并不是免费的。客户端需要持有、传输和维护足够多的仓库对象，而这在超大规模、高频操作的场景下可能变得昂贵。

举个例子：**一个 CI 任务可能只想知道某次提交相对于主分支修改了哪些文件。** 在典型的 Git 工作流中，它需要获取必要的仓库对象并在本地计算，或者依赖平台提供的专用 API。但在 Scion 中，任务可以直接向服务端请求 Diff，甚至不需要创建本地工作副本。

<ScionDiagram variant="diff" />

另一个例子是仓库缓存。Anthropic 曾经使用预先准备的仓库快照（Seeds）来减少重复下载。但随着每天的 Merge 数量快速增长，这些快照在两次刷新之间会落后主分支越来越多的变更，更新成本不断增加。

这揭示了一个矛盾：**许多任务实际需要的数据很少，但为了支持本地独立操作，系统却可能需要处理和维护远超任务需求的数据。**

## 三、客户端普遍在线，设计取舍可以重选

而 Anthropic 的大量 Agent 和 CI 任务在运行时都能够访问中心服务器。这意味着，Git 为离线自主性做出的设计取舍，在这一工作负载下可能已经不再划算。

Anthropic 并非没有尝试优化 Git。他们使用过 Shallow Clone、Sparse Checkout、仓库快照，以及数百台 Git Mirror。但这些手段逐渐变得复杂且难以扩展。

因此，他们开始重新审视 Git 的基础设计假设：

**既然客户端普遍在线，能否放弃部分本地自主性，让服务端承担更多计算，使操作成本尽可能与实际需要的数据量或变更规模相关，而不是与整个仓库规模相关？**

Scion 正是这一新设计权衡的产物。

## 四、AI 也降低了重新构建系统的成本

但故事并没有停在这里。

**AI 不仅改变了系统需要承受的工作负载，也改变了构建新系统的成本。**

过去，重新设计一套版本控制系统意味着高昂的研发投入、长期测试和复杂迁移。因此，即使现有架构并不理想，继续优化它也可能是更经济的选择。

如今，Agent 大幅提高了软件实现、测试和优化的效率，使得重新构建复杂系统的成本开始下降。

Anthropic 在文章中分享了一个例子：他们让 Claude Mythos Preview 重写早期手工实现的 Git-to-Scion 数据导入管线。新版本在保持原有约束的同时，内存消耗降低了 20 倍，运行速度提高了 4 倍。

最终，一个只有七名工程师的团队，在五个月内完成了 Scion、代码审查系统 Antique 及多个相关系统的建设和迁移。

当然，AI 提高编码效率并不意味着系统迁移、可靠性验证和长期维护可以忽略。但它确实改变了重新设计的经济性。

## 五、重新设计的必要性与可行性，同时上升

**因此，AI 同时改变了架构重新设计的必要性与可行性：**

- **必要性上升：** 新工作负载使旧架构的性能和维护成本持续增长。
- **可行性上升：** AI 降低了新系统的实现与优化成本，使原本昂贵的重构方案变得更加现实。

<ScionDiagram variant="economics" />

两者共同改变了「继续优化」与「重新设计」之间的权衡。

Scion 正是在这一背景下重新审视设计假设、重新选择架构权衡的产物。

**AI 不仅改变了我们需要构建什么样的系统，也改变了我们能够以什么样的成本构建系统。**
