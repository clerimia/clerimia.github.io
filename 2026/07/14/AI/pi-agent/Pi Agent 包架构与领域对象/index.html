Pi Agent 包架构与领域对象

发表于2026-07-14|更新于2026-07-15|技术AIpi-agent
|浏览量:

【clerimia：】 之前写了《Pi Agent 设计思路》，从 AgentLoop -> Agent -> Providers 三层纵向拆解了引擎。但那只是 pi-agent monorepo 中 packages/agent 一个包的故事。这次把视角从「分层」切换到「分包」，横向看 5 个包各自的职责、领域对象和依赖关系，补完整个 monorepo 的拼图。

pi-agent monorepo 包含 5 个包，依赖方向从底到顶：

包 npm 名 定位
pi-ai @earendil-works/pi-ai LLM 传输层：统一 API、provider 注册表、auth 解析、流式调用
pi-tui @earendil-works/pi-tui 终端 UI 层：差分渲染引擎、组件系统、键盘输入（零 Agent 感知）

【clerimia：】 注意 pi-tui 和 pi-ai 都是叶子包，互不依赖。pi-tui 甚至不知道 Agent 的存在–它是个纯粹的终端 UI 库。这种「UI 和引擎完全解耦」的设计让 UI 可以独立复用。

1. pi-ai：LLM 传输层

统一 LLM API，提供 provider 集合、自动 auth 解析、token/cost 追踪。
只包含支持 tool calling 的模型，因为这是 agentic workflow 的硬需求。

核心领域对象

领域对象 类型 职责
Model<TApi> interface 模型定义：id / name / api / provider / baseUrl / reasoning / input / cost / contextWindow / maxTokens / compat
Provider<TApi> interface provider 运行时单元：id / name / auth / getModels() / stream() / streamSimple()
Models interface provider 集合 + auth 应用 + stream 便利方法。getModels() / getModel() / getAuth() / streamSimple()
Message type UserMessage | AssistantMessage | ToolResultMessage
Context interface 发给 LLM 的请求上下文：{ systemPrompt?, messages, tools? }
AssistantMessageEvent type 流式事件联合（12 种：start / text_start / text_delta / text_end / thinking_* / toolcall_* / done / error）
AssistantMessageEventStream class 事件流，可 for await 消费，也可 .result() 获取最终消息
StreamFn type (model, context, options?) => AssistantMessageEventStream。契约：不抛异常，失败编码进流
Tool<TParameters> interface 工具定义：name / description / parameters（TypeBox schema）
Usage interface token 统计：input / output / cacheRead / cacheWrite / reasoning / totalTokens / cost
StopReason type "stop" | "length" | "toolUse" | "error" | "aborted"
ThinkingLevel type "minimal" | "low" | "medium" | "high" | "xhigh" | "max"
Transport type "sse" | "websocket" | "websocket-cached" | "auto"
ProviderAuth type 认证方式：ApiKeyAuth | OAuthAuth（每个 provider 必须至少有一种）
CredentialStore interface 凭证存储抽象（读写 API key / OAuth token）

关键设计

两套 API 并存：

  • 新 API（推荐）：createModels() + provider 工厂（如 anthropicProvider()）-> models.streamSimple(model, context, options)
  • 旧 API（compat 层）：全局 streamSimple() / completeSimple()，从环境变量自动解析 API key

【clerimia：】 compat.d.ts 的注释明确说「This module is deleted with the coding-agent ModelManager migration」–旧 API 是过渡产物。

Provider 注册表：KnownProvider 联合类型列出了 30+ 个内置 provider（anthropic / openai / google / xai / groq / openrouter / bedrock / mistral / 深度寻求 等）。每个 provider 有独立的工厂函数（anthropicProvider() / openaiProvider() 等），按需引入以减小包体积。

Compat 兼容层：OpenAICompletionsCompat 接口定义了 20+ 个兼容开关（thinkingFormat / cacheControlFormat / supportsStrictMode 等），让任意 OpenAI 兼容 API（Ollama / vLLM / LM Studio 等）都能正确工作。

2. pi-tui：终端 UI 层

从零实现的终端 UI 框架，不依赖 ink / blessed。核心特性是差分渲染 + 同步输出（CSI 2026），实现无闪烁的交互式 CLI。

核心领域对象

领域对象 类型 职责
TUI class 主渲染器：差分渲染引擎 + 组件树 + 焦点管理 + Overlay 浮层 + IME 光标定位
Terminal interface 终端抽象：start / stop / write / columns / rows / hideCursor / clearScreen
ProcessTerminal class Terminal 的生产实现，用 process.stdin/stdout + raw mode + Kitty keyboard 协商
Component interface 组件接口：render(width): string[] + handleInput?(data) + invalidate()
Focusable interface 可聚焦组件：focused: boolean
Container class 基础容器：addChild() / removeChild() / clear()
Editor class 多行编辑器（2333 行）：word wrap / slash 补全 / Tab 文件补全 / Emacs 快捷键 / 撤销栈
Markdown class Markdown 渲染组件，支持语法高亮回调
SelectList class 交互式选择列表
Input class 单行输入
Image class 内联图片（Kitty / iTerm2 图形协议）
Key object 按键标识符构造器：Key.ctrl("c") / Key.shiftTab 等，编译期类型安全
KeybindingsManager class 键绑定管理：默认绑定 + 用户自定义 + 冲突检测
StdinBuffer class stdin 缓冲：把分批到达的数据拆分为完整转义序列
CombinedAutocompleteProvider class 自动补全：slash 命令 + @ 文件路径 fuzzy 搜索

关键设计

三路键盘协议兼容：keys.ts（1400 行）同时处理 Kitty CSI-u / xterm modifyOtherKeys / legacy 三种键盘协议的输入解析。ProcessTerminal 在启动时协商协议，isKittyProtocolActive() 全局状态影响 legacy 序列的歧义解释。

差分渲染：TUI.doRender() 实现三策略–首次渲染全量 / 尺寸变化全量重绘 / 正常更新只渲染变化行。所有输出包裹在 \x1b[?2026h ... \x1b[?2026l（synchronized output）中。

Overlay 系统：showOverlay(component, options) 支持模态浮层，9 种锚点定位、百分比/绝对定位、焦点恢复状态机。

原生模块：native/win32/ 和 native/darwin/ 各有 C 模块处理平台特定的输入问题（Windows 的 VT 输入模式、macOS 的修饰键检测）。

【clerimia：】 pi-tui 是 monorepo 里的叶子库，零 @earendil-works/ 依赖。它不知道 Agent 的存在，通过 Component 接口向上提供扩展点。消费方（coding-agent）创建 TUI 实例，在 editor.onSubmit 回调中调用 Agent 逻辑，把响应渲染为新的 Markdown 组件。

3. pi-agent-core：Agent 引擎层

通用 Agent 引擎，建立在 pi-ai 之上。两层架构：低层 Agent + runAgentLoop 是纯运行时引擎；高层 AgentHarness 叠加 session 持久化、compaction、hook 系统。

核心领域对象

3.1 引擎层

领域对象 类型 职责
runAgentLoop() function 核心 agent 循环（callback 式）：双层 while 循环，外层处理 follow-up，内层处理 tool calls + steering
agentLoop() function 流式工厂（返回 EventStream，可 for await）
AgentMessage type Message | CustomAgentMessages[keyof CustomAgentMessages]。核心联合类型，通过 declaration merging 扩展
AgentContext interface 传入 loop 的快照：{ systemPrompt, messages, tools? }
AgentState interface Agent 公开状态：systemPrompt / model / thinkingLevel / tools / messages + 只读 isStreaming / streamingMessage / pendingToolCalls / errorMessage
AgentEvent type 生命周期事件联合（10 种：agent_start/end / turn_start/end / message_start/update/end / tool_execution_start/update/end）
AgentLoopConfig interface 循环配置：model / convertToLlm（必填）/ transformContext? / shouldStopAfterTurn? / getSteeringMessages? / getFollowUpMessages? / beforeToolCall? / afterToolCall?
AgentTool<TParameters, TDetails> interface 工具定义：继承 Tool，加 label / execute / executionMode? / prepareArguments?
StreamFn type 调用 LLM 的函数签名（从 pi-ai 导入）

3.2 Agent 类

领域对象 类型 职责
Agent class 低层 agent loop 的有状态封装。拥有 transcript（AgentState），管理生命周期事件，执行工具，暴露 steering/follow-up 队列
PendingMessageQueue class 消息队列："all" / "one-at-a-time" 两种 drain 模式
ActiveRun type { promise, resolve, abortController } – 运行中的任务凭证

Agent 的关键方法：prompt() / continue() / steer() / followUp() / abort() / waitForIdle() / reset() / subscribe()

【clerimia：】 Agent 不掌握 Session！它只有一个 sessionId?: string（给 provider 做 cache key 用的字符串），对话记录是 _state.messages: AgentMessage[] 纯内存数组。持久化是上层的事。

3.3 AgentHarness 类（高层编排器）

领域对象 类型 职责
AgentHarness class 高层编排器，直接调 runAgentLoop()（绕过 Agent）。拥有 session 持久化、compaction、branch 导航、skills/prompt-templates 资源管理、hook 系统
AgentHarnessPhase type "idle" | "turn" | "compaction" | "branch_summary" | "retry" – 操作锁状态机
Session class 会话树操作层：从 leaf 到 root 重建 context，各种 entry 的 append
SessionTreeEntry type 会话树条目联合：MessageEntry / CompactionEntry / BranchSummaryEntry / ModelChangeEntry / ThinkingLevelChangeEntry / ActiveToolsChangeEntry / CustomEntry / CustomMessageEntry / LabelEntry / LeafEntry
SessionStorage<TMetadata> interface entry 级 CRUD + getPathToRoot + getLabel
SessionRepo interface session 级 CRUD：create / open / list / delete / fork
ExecutionEnv interface FileSystem + Shell 组合接口，平台无关的 I/O 抽象（所有方法返回 Result<T, Error>，永不抛异常）
AgentHarnessError class 顶层错误归一化（code: busy / invalid_state / session / hook / auth / compaction / …）
Skill interface 技能：name / description / content / filePath / disableModelInvocation?
PromptTemplate interface 提示模板：name / description? / content（含 $1 / $@ 占位符）

AgentHarness 的关键方法：prompt() / skill() / promptFromTemplate() / steer() / followUp() / nextTurn() / compact() / navigateTree() / abort() / subscribe() / on()

3.4 Compaction（上下文压缩）

领域对象 类型 职责
prepareCompaction() function 找 cut point，分割出要摘要的消息
compact() function 执行摘要生成（调用 LLM），处理 split-turn
shouldCompact() function 阈值判断：contextTokens > contextWindow - reserveTokens
generateSummary() function 单次摘要生成，支持 previousSummary（增量更新）
generateBranchSummary() function 分支摘要（用于 tree 导航时摘要被放弃的分支）
CompactionSettings interface enabled / reserveTokens（默认 16384）/ keepRecentTokens（默认 20000）

关键设计

AgentMessage 可扩展性：CustomAgentMessages 是空接口，下游包通过 declaration merging 添加自定义 message 角色（如 coding-agent 的 bashExecution / compactionSummary / branchSummary）。convertToLlm 是唯一的 LLM 边界转换点，把自定义类型转成 LLM 能理解的 Message[]。

两层架构演进：AgentHarness 曾依赖 Agent，现已移除依赖直接调 runAgentLoop()。但 coding-agent 还没迁移到 AgentHarness（状态 Planned），仍用自己的 AgentSession。

Session 树模型：每条 entry 有 id 和 parentId 形成树结构，“leaf” 指针跟踪当前位置。branching 把 leaf 移到更早的 entry，允许新分支而不修改历史。buildContext() 从 leaf 到 root 路径重建 context。

【clerimia：】 这个包是整个框架的心脏。AgentLoop 是引擎，Agent 是旧产品壳，AgentHarness 是新编排层（还在 scratch 阶段）。三层并存是过渡期状态。

4. pi-coding-agent：编码 Agent 产品层

Coding agent CLI，内置 read / bash / edit / write 工具和会话管理。刻意不内置 sub-agents / plan mode / 权限弹窗 / MCP，而是通过 Extensions / Skills / Prompt Templates 把工作流外置。

核心领域对象

4.1 AgentSession – 核心中的核心

领域对象 类型 职责
AgentSession class Agent 生命周期与会话管理的核心抽象（3246 行）。封装 agent 状态访问、事件订阅 + 自动 session 持久化、模型/thinking 管理、手动/自动 compaction、bash 执行、session 切换/分支、extension 系统绑定
AgentSessionConfig interface 构造参数：agent + sessionManager + settingsManager + cwd + scopedModels + resourceLoader + customTools + modelRegistry
AgentSessionEvent type AgentSession 对外的事件联合

AgentSession 的关键方法：

  • 提示：prompt() / steer() / followUp() / sendCustomMessage()
  • 控制：abort() / waitForIdle()
  • 模型：setModel() / cycleModel() / setThinkingLevel() / cycleThinkingLevel()
  • Compaction：compact() / abortCompaction() / setAutoCompactionEnabled()
  • Session 树：navigateTree() / getSessionStats() / exportToHtml()
  • Extension：bindExtensions() / reload() / hasExtensionHandlers()

【clerimia：】 AgentSession 持有 agent: Agent 和 sessionManager: SessionManager。它在合适时机把 SessionManager 构建的消息塞回 Agent 的 state.messages–Agent 自己不会读磁盘。AgentSession 和 pi-agent-core 的 AgentHarness 在职责上高度重叠，都是「Agent + 持久化 + 产品级能力」的组合器，是两代编排层并存。

4.2 SessionManager

领域对象 类型 职责
SessionManager class 把会话作为 append-only 树存储在 JSONL 文件中。每条 entry 有 id 和 parentId 形成树结构，leaf 指针跟踪当前位置
SessionEntry type 树条目联合：message / thinking_level_change / model_change / compaction / branch_summary / custom / custom_message / label / session_info
SessionContext interface { messages, thinkingLevel, model } – 从树路径重建的上下文

关键方法：create() / open() / continueRecent() / inMemory() / forkFrom() / appendMessage() / appendCompaction() / buildSessionContext() / branch() / createBranchedSession()

4.3 其他核心领域对象

领域对象 类型 职责
SettingsManager class 从 global（~/.pi/agent/settings.json）和 project（.pi/settings.json）两个 scope 加载设置，deep-merge。约 50 个配置字段，部分持久化（只 merge 修改字段）
ModelRegistry class 加载管理模型（builtin + custom from models.json），通过 AuthStorage 解析 API key。支持 provider 级 override 和动态 provider 注册（来自 extensions）
AuthStorage class API key / OAuth 凭证的持久化存储
createAgentSession() function SDK 高层入口：用指定 options 创建一个 AgentSession，所有参数可选
AgentSessionRuntime class 持有当前 AgentSession 及其 cwd-bound services，提供 session 替换操作（switch / new / fork / import）
ExtensionRunner class 扩展系统运行时：加载 TypeScript 扩展、注册工具/命令/hook、事件转发
ToolDefinition interface 工具定义（含 schema + prompt snippet + guidelines），比 AgentTool 更丰富
buildSystemPrompt() function 构建系统提示词：工具列表 + guidelines + context files + skills

4.4 内置工具

7 个工具，每个有 createXxxToolDefinition(cwd, options) 工厂：

工具 职责
read 读文件（截断 + 高亮）
bash 执行 shell 命令（支持 spawn hook、输出捕获）
edit 编辑文件（精确替换 + diff 生成）
write 写文件
grep 内容搜索（ripgrep 封装）
find 文件搜索
ls 列目录

默认启用 ["read", "bash", "edit", "write"]，grep / find / ls 可选启用。

4.5 自定义消息类型

通过 declaration merging 扩展 CustomAgentMessages：

消息类型 职责
BashExecutionMessage bash 命令执行记录（command / output / exitCode / cancelled / truncated）
CompactionSummaryMessage compaction 摘要
BranchSummaryMessage 分支摘要
CustomMessage<T> 扩展自定义消息

convertToLlm() 把这些自定义类型转换为 LLM 能理解的 Message[]（通常包装为 user message + 特殊标记）。

运行模式

模式 触发 用途
interactive 默认（TTY） 全屏 TUI
print -p 或非 TTY 单次提示，输出纯文本后退出
json --mode json 输出所有事件为 JSON lines
rpc --mode rpc 进程集成，stdin/stdout JSONL 协议
SDK 编程调用 createAgentSession() 嵌入第三方 app

关键设计

Extension 系统全外置：不内置 sub-agents / plan mode / 权限弹窗 / MCP，而是通过 TypeScript Extensions 让用户自己实现。扩展可以注册工具、命令、hook（before_provider_request / before_provider_payload / after_provider_response / before_tool_call / after_tool_call / session_before_compact 等）、UI 组件、provider。

资源来源追踪：ResourceLoader 发现并加载 extensions / skills / prompt-templates / themes / context files（AGENTS.md / CLAUDE.md），每个资源带来源元数据（global / project / extension）。

自动 Compaction：两种触发–overflow（LLM 返回 context overflow，移除错误消息后 compact-and-retry，仅一次）vs threshold（接近上限，compact 但不 retry）。

【clerimia：】 这个包是"产品壳"，把 pi-agent-core 的引擎 + pi-ai 的 LLM 能力 + pi-tui 的 UI 组装成一个可用的 coding agent。AgentSession 是它的核心粘合剂。但它还在用旧的 Agent（不是 AgentHarness），迁移计划状态是 Planned。

5. pi-orchestrator：多实例进程编排层

实验性的多实例进程编排器。管理多个 pi agent 子进程的生命周期、RPC 转发、远程在线状态。不是任务级的多 Agent 协作编排。

核心领域对象

领域对象 类型 职责
OrchestratorSupervisor class 中枢：维护 Map<string, LiveInstance>，管理 spawn / stop / RPC 转发 / 崩溃恢复
LiveInstance type 运行中实例：record + resources（rpcProcess / radiusPiId / sessionId）+ subscribers
InstanceStatus type "starting" | "online" | "stopping" | "stopped" | "error"
InstanceRecord interface 持久化记录：id / status / cwd / createdAt / lastSeenAt / label / sessionId / sessionFile / radiusPiId
RpcProcessInstance class spawn 一个 pi --mode rpc 子进程，通过 stdin/stdout JSONL 通信
RadiusPresence class 管理机器和 Pi 实例在 radius.pi.dev 上的在线状态（HTTP 心跳）
IPC 协议 - Unix socket（~/.pi/orchestrator/orchestrator.sock）上的 JSONL 请求/响应

关键设计

进程外编排：orchestrator 不直接 import Agent / AgentSession，只通过 RPC 类型（RpcCommand / RpcResponse / AgentSessionEvent）间接关联。它 spawn 一个 pi --mode rpc 子进程，子进程内部才跑 AgentSession。orchestrator 只持有子进程的 stdin/stdout 句柄。

Radius 远程在线（可选）：radius.pi.dev 是一个在线状态服务。pi 实例注册后定期心跳，其他机器可以查询哪些 pi 实例在线。容错策略：404 连续 3 次后 re-registration，非 404 用指数退避。

CLI：orchestrator serve 启动 daemon / list / spawn / stop / status / rpc / rpc-stream

【clerimia：】 这个包很小（约 1500 行）、很新（CHANGELOG 全空）、实验性。它的 “orchestration” 语义是「进程池管理 + RPC 网关 + 远程在线」，不是 LangGraph / CrewAI 那种任务编排。没有任务分发、agent 间通信、共享上下文。每个 pi 实例完全独立。

层级职责一句话

层 包 一句话
传输层 pi-ai 统一 LLM API，不管 Agent 逻辑
UI 层 pi-tui 终端渲染，不管 Agent 逻辑
引擎层 pi-agent-core Agent 循环 + 状态 + 持久化，不管具体工具

【clerimia：】 这个分层非常干净：每层只依赖下一层，不知道上层的存在。pi-ai 不知道 Agent，pi-agent-core 不知道 coding 工具，pi-coding-agent 不知道多实例。唯一的例外是 pi-orchestrator 直接依赖 pi-coding-agent（因为要 spawn pi --mode rpc 子进程）。这种单向依赖链让每一层都可以独立复用。

架构演进观察

从代码中可以看到几个正在进行的迁移：

  1. Agent -> AgentHarness：pi-agent-core 的 AgentHarness 已完成基础（session、compaction、hook），但 coding-agent 还没迁移（AgentSession 仍用 Agent）。状态：Planned。

  2. 全局 API -> Models 实例：pi-ai 的 compat 层（全局 streamSimple()）标注为 deprecated，新 API 是 createModels() + provider 工厂。compat 层将在 coding-agent 迁移完成后删除。

  3. AgentSession -> AgentHarness：AgentSession（coding-agent 包）和 AgentHarness（pi-agent-core 包）在职责上高度重叠。长期看 AgentHarness 应该取代 AgentSession，但目前两者并存。

【clerimia：】 三条迁移线指向同一个方向：把更多能力从产品层下沉到引擎层。Session 持久化、compaction、hook 系统这些「产品级能力」正在从 coding-agent 的 AgentSession 往 pi-agent-core 的 AgentHarness 搬。完成后 coding-agent 会变成一个薄薄的产品壳–只保留 coding 工具、扩展系统和 CLI，核心编排能力由 AgentHarness 提供。
