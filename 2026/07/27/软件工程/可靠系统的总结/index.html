韧性工程四能力：一个思维框架与示范挂载

发表于2026-07-27|更新于2026-07-27|技术软件工程
|浏览量:

可靠的系统不是没有失败，而是失败可以被发现、预防、处理、恢复，并从中学习。

把这句拆开，正好对应 Erik Hollnagel 韧性工程的四能力。本文把这四能力当作一个思维框架–每个能力是一个"挂钩"，挂钩上可挂不同的实现方案；下半篇用 Spring AOP 在其中一个挂钩上做一次示范挂载，展示"挂上去长什么样"。

一、 理论基石：韧性工程四大能力

基于 Erik Hollnagel 的 Resilience Engineering 框架，一个系统能否在扰动下持续保持所需表现，取决于四种潜能（potentials）是否到位。注意原文用词是动词形式，且 Hollnagel 反复强调韧性是表现（performance）而非属性（property）–系统不存在"具备韧性"这种状态，只有"在扰动下表现出了韧性"这种过程。

能力 原文动词 Hollnagel 的定义（knowing…） 这个能力服务什么
可响应 Respond knowing what to do 对已发生的扰动有应对手段
可观测 Monitor knowing what to look for 让发生的一切被看见
可预防 Anticipate knowing what to expect 提前预判风险并前置拦截
可学习 Learn knowing what has happened 从经验中沉淀，让下次更好

四能力相互依赖、不可替代–Hollnagel 明确指出"某一项的缺失无法被其他项的增强补偿"。例如：Respond 依赖 Monitor（得先看见故障才能响应），Learn 又依赖 Monitor 的数据。

二、 思维框架：能力是视角，实践是挂载

2.1 框架的核心观念：能力 ≠ 实现

很多人把"四能力"和"某种具体实现"焊死–比如一提 Respond 就想到重试、一提 Learn 就想到审计。但 Hollnagel 的四能力是视角，不是实现。同一个"应对故障"的需求（Respond 视角），可以挂重试、挂降级、挂人工兜底，方案是可选的。

所以本文把笔记组织成：每个能力是一个"挂钩"，挂钩上列出可选的实践方案；下半篇只挑一个挂钩做一次示范挂载。这样框架本身不绑死任何实现，换语言、换框架都能用。

2.2 四个挂钩与其上的可选方案

挂钩按闭环递进排序：先看见（Monitor）才能响应（Respond），响应够了还要能预防（Anticipate），最后从一切中学习（Learn）。

挂钩 服务目标 挂钩上的可选方案
Monitor（可观测） 让"发生的一切"被看见 Trace、Metric、Log、Audit
Respond（可响应） 让"已发生的扰动"被应对 重试、断路器、降级、超时、舱壁隔离、补偿（Saga / BASE / TCC）、告警触发
Anticipate（可预防） 让"该被拦的"在执行前被拦 限流（令牌桶 / 漏桶）、幂等、参数校验、前置条件
Learn（可学习） 让"发生过的事"沉淀为"下次更好" 事后复盘、阈值调优、规则沉淀、混沌演练、故障入库

2.3 跨挂钩复合模式

上一节把每个实践按"主要服务的能力"归进一个挂钩，但有些实践天生跨多个挂钩，硬归一个会失真。这类"复合模式"值得单独点明，避免被追问"它到底是哪个能力"时卡壳。

复合模式 跨的挂钩 拆解
补偿（Saga / BASE / TCC） Respond + Learn 执行时是 Respond（恢复一致），补偿记录供事后 Learn（复盘为什么需要补偿）
告警闭环 Respond + Learn 触发时是 Respond（响应故障），告警聚合后的趋势供 Learn（发现系统性问题）
对账恢复（Audit-based Reconciliation） Monitor + Respond 用 audit 数据对账发现不一致（Monitor），发现后执行修复动作恢复一致（Respond）。audit 数据本身是 Monitor 基础设施，是它"被读了干嘛"决定了驱动哪个能力
审计日志 Monitor + Learn 写入时偏 Monitor（留痕可查），用途上可驱动 Learn（复盘），也可驱动 Respond（对账恢复）

规律：复合模式都是"某数据/动作被读后驱动了下一个能力"。Saga 的补偿记录被复盘读-> Learn；audit 被对账读-> 驱动 Respond；告警被趋势分析读-> Learn。驱动者 ≠ 被驱动的数据，别把数据本身归到它驱动的能力上。

2.4 正交 vs 内聚：挂钩如何挂载的指导原则

把能力挂载到系统时，先分清哪些是切面/模块内聚的、哪些是系统级正交的。判别法：如果把这块挂载删掉，这个能力还在不在？

  • 限流、重试、断路器、降级、补偿 – 删掉挂载它们就没了，是内聚实现。
  • Trace、Metric、Log、Audit – 删掉任何具体挂载它们还在。HTTP 入口还在打 trace，数据库层还在打 log。这套基础设施是系统级正交的，挂载只是它的使用者。

一个反直觉点：观察 vs 控制。可观测本身不驱动弹性–关掉 metrics，限流照样挡，重试照样跑，你只是"瞎了"。真正"做"弹性的是控制组件（限流器抛异常、熔断器开闸、重试再调 proceed）。可观测是弹性的前提条件而非驱动器：控制组件消费可观测数据作为决策输入，才间接驱动了弹性。

一个灰色地带：熔断器内部维护的"滑动窗口失败计数"本质是一份 metric，但由熔断器自持、不进通用 metrics 系统。这份计数既是观察（记失败率）又是控制（决定开闸），是个灰色地带。承认它，比硬归类更贴合真实系统。

2.5 挂载方式本身也是可选的

同一个挂钩，可用不同的挂载机制接入系统：

挂载方式 适用 代价
AOP 切面（Spring @Around） 进程内、声明式、业务低侵入 只能管进程内单次调用
响应式拦截（Interceptor / Filter） Web/MQ 入口、同步阻塞少 管不了方法内部的重试
编排器 / Orchestrator 跨服务长事务、Saga 协调 重，需独立服务
中间件 / Sidecar（Service Mesh） 跨语言、统一治理 基础设施重

下文示范用 AOP 切面挂载，因为它最适合讲清"声明式 + 低侵入"，但要记住它不是唯一挂载方式。

三、 示范挂载：用 Spring AOP 挂载 Respond 挂钩

本节范围声明：仅用 AOP 挂载 Respond 挂钩中的 重试 + 断路器 + 降级。Anticipate（限流/幂等）、Monitor（可观测基础设施）、Learn（复盘/调优）作为挂钩存在于框架层，但不在本示范的代码实现内–它们是正交基础设施或另一套挂载，不在本切面职责范围。补偿（Saga/BASE/TCC）也属于 Respond 挂钩，但因涉及分布式、复杂度高，留在框架层做选型对比，不在本示范落地。

3.1 设计选择：为什么只用一个 @Around

韧性的核心是控制执行流–重不重试、降不降级、开不开闸。在 Spring AOP 的通知里，只有 @Around 能控制 proceed()（决定是否执行、执行几次、替换返回值），@Before / @After 等都是观察者，只能记录、不能干预。

所以这里把重试、断路器、降级全部收进单个 @Around，让状态留在方法栈上，避免多通知之间靠上下文传参产生的可见性坑。代价是方法变长，换来的是执行顺序一目了然、状态自洽。

3.2 注解：声明式激活

@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface Resilience {

    // [Respond] 重试
    int maxRetries() default 0;
    Class<? extends Throwable>[] retryOn() default {};

    // [Respond] 断路器
    String circuitBreakerName() default "";

    // [Respond] 降级
    String fallbackMethod() default "";
}

3.3 切面内聚状态

按 2.4 的正交原则，切面只持有内聚执行态；可观测基础设施（metrics）通过 @Autowired 注入，traceId 通过 MDC.get("traceId") 直接取，不再包一层"上下文对象" --那是无意义的间接。

/**
 * 切面内聚状态：单机内一次方法调用的执行态。
 * 生命周期 = 一次 @Around 调用，结束后丢弃；不跨请求、不跨机器。
 */
@Data
public class ResilienceState {
    private long startNanos;
    private boolean degraded;
    private int retryAttempts;
    private boolean circuitOpen;
    private boolean finalSuccess;
    private Throwable finalException;
}

3.4 切面：单个 @Around 串起重试 / 断路器 / 降级

@Aspect
@Component
public class ResilienceAspect {

    // [Monitor·L1正交] 正交基础设施，直接注入，不包上下文
    @Autowired private MetricsCollector metricsCollector;
    @Autowired private CircuitBreakerManager circuitBreakerManager;

    @Around("@annotation(resilience)")
    public Object aroundAdvice(ProceedingJoinPoint pjp, Resilience resilience) throws Throwable {
        ResilienceState state = new ResilienceState();
        state.setStartNanos(System.nanoTime());

        // ───── Respond：断路器前置闸门 ─────
        // ⚠️ cb.allowRequest() / recordSuccess() / recordFailure() 读写的是熔断器内部
        // 维护的"滑动窗口失败计数"--它本质是一份 metric，但由熔断器自持、
        // 不进通用 metrics 系统。这是"既是观察又是控制"的灰色地带：
        // recordFailure 是记录，但累积到阈值后 allowRequest 返回 false 即为控制。
        CircuitBreaker cb = null;
        if (StringUtils.hasText(resilience.circuitBreakerName())) {
            cb = circuitBreakerManager.get(resilience.circuitBreakerName());
            if (!cb.allowRequest()) {
                state.setCircuitOpen(true);
                metricsCollector.counter("circuit.open").increment();
                // 熔断开启时直接走降级，不进重试
                return doFallback(pjp, resilience,
                    new CircuitOpenException(resilience.circuitBreakerName() + " circuit open"),
                    state);
            }
        }

        // ───── Respond：重试循环 ─────
        int currentAttempt = 0;
        Throwable lastException = null;
        Object result = null;

        while (currentAttempt <= resilience.maxRetries()) {
            try {
                result = pjp.proceed();
                if (cb != null) cb.recordSuccess();
                state.setFinalSuccess(true);
                return result;
            } catch (Throwable t) {
                lastException = t;
                if (cb != null) cb.recordFailure();

                boolean isRetryable = isRetryableException(t, resilience.retryOn());
                // 不可重试，或已是最后一次尝试：退出循环
                if (!isRetryable || currentAttempt == resilience.maxRetries()) break;

                currentAttempt++;
                state.setRetryAttempts(currentAttempt);
                metricsCollector.counter("retry.attempt").increment();

                // 指数退避 × 随机抖动：抖动乘进退避值，避免雪崩同步重试。
                // ⚠️ 生产环境勿用 Thread.sleep 阻塞工作线程--尤其是 Agent /
                // 异步场景。应交由调度器（ScheduledExecutor / 响应式 delay）延迟重试：
                //   scheduler.schedule(() -> retryQueue.offer(pjp), backoffMillis, MS);
                long base = (long) Math.pow(2, currentAttempt) * 1000;
                long backoffMillis = (long) (base * (0.5 + Math.random() * 0.5));
                Thread.sleep(backoffMillis); // 仅作演示
            }
        }

        // ───── Respond：降级 ─────
        if (lastException != null) {
            return doFallback(pjp, resilience, lastException, state);
        }
        return result;
    }

    private Object doFallback(ProceedingJoinPoint pjp, Resilience resilience,
                              Throwable cause, ResilienceState state) throws Throwable {
        state.setDegraded(true);
        state.setFinalException(cause);
        if (StringUtils.hasText(resilience.fallbackMethod())) {
            metricsCollector.counter("fallback.triggered").increment();
            return invokeFallbackMethod(pjp, resilience.fallbackMethod(), pjp.getArgs(), cause);
        }
        throw cause;
    }
}

3.5 关于 Monitor / Learn 在本示范的边界

本示范不实现 Monitor 和 Learn，但它们的"接入点"在代码里清晰可见：

  • Monitor 接入点：metricsCollector.counter(...) 那几行就是切面往正交可观测基础设施里埋点（L2 层）。这些基础设施由系统提供，切面只是使用者。
  • Learn 接入点：本切面不持有。真正的 Learn（复盘、调优、混沌演练）发生在切面之外，基于 Monitor 产生的数据做事后分析。切面能做的是把足够的数据喂给 Monitor，让 Learn 有料可学。

一句话：切面负责 Respond 的控制 + Monitor 的埋点；Learn 是框架层的能力，由人/平台基于数据去做，不在这段代码里。

四、 业务侧：低侵入接入

业务代码只需关注核心逻辑，通过 @Resilience 声明式激活能力：

@Service
public class OrderService {

    @Resilience(
        circuitBreakerName = "paymentService",
        maxRetries = 3,
        retryOn = { TransientException.class, TimeoutException.class },
        fallbackMethod = "createOrderFallback"
    )
    public OrderVO createOrder(CreateOrderRequest request) {
        // 核心业务逻辑，无需感知重试/熔断/降级
        inventoryService.deductStock(request.getSkuId(), request.getQty());
        paymentService.pay(request.getUserId(), request.getAmount());
        return orderRepository.save(request);
    }

    // 降级兜底：返回待审核状态，后续人工或定时任务处理
    public OrderVO createOrderFallback(CreateOrderRequest request, Exception ex) {
        return OrderVO.builder()
            .status(OrderStatus.PENDING_REVIEW)
            .message("系统繁忙，订单已挂起")
            .build();
    }
}

注：createOrder 真要落地还需考虑跨服务的数据一致性（库存扣了但订单没建怎么办），那属于 Respond 挂钩上的补偿方案（Saga / BASE / TCC），见 2.2 的挂钩表。本示范只展示单机内的重试/降级，不碰补偿–它在框架层是独立可选方案，不在本切面职责内。

五、 总结

维度 传统系统 韧性系统
失败感知 用户报错，日志散落 Trace 串联，Metric 实时告警
失败预防 依赖人工测试 限流 + 幂等自动拦截
失败处理 直接抛出，流程中断 重试自愈、降级兜底、断路器隔离
失败恢复 数据不一致，需人工修 补偿（Saga/BASE/TCC）自动回滚或重试到一致
从失败学习 出了事就过去了 复盘、调优、混沌演练，让下次更好

结论：Hollnagel 的四能力是思维框架，不是一套固定实现。把每个能力当作挂钩，挂载限流/重试/断路器/补偿/可观测等可选方案，再用某种挂载机制（AOP / 编排器 / Sidecar）接入系统。本文用 Spring AOP 在 Respond 挂钩上挂了"重试 + 断路器 + 降级"做示范，其余挂钩上的方案留在框架层做选型对比。韧性的本质不是消灭失败，而是让每一次失败都落在"可发现 -> 可预防 -> 可处理 -> 可恢复 -> 可学习"的闭环里。
